# COC'S

[English](README.md)

COC'S는 건설 ERP 프로젝트의 실제 구현 코드와 엔지니어링적 판단 중 일부를 소개하는 저장소입니다. 이음아이앤씨와 계약하여 한국비즈텍의 ERP 시스템 구축에 참여했으며, 개발팀장으로서 Spring Boot 아키텍처 설계와 공통 코드 구현을 주도했습니다.

시스템은 사용자 관리, 공정 관리, 품의·결재, 실적 집계 등 건설 업무를 지원했습니다. 회사로부터 비상업적 포트폴리오 공개 허가를 받은 팀 프로젝트이며, 공개 조건은 [LICENSE](LICENSE)에 기록되어 있습니다.

## 담당 역할

- 백엔드 아키텍처와 Spring Boot 모듈 구조 설계.
- 페이지 공통 구조, 사용자 권한 제어, 메뉴 바인딩과 SBUx 연동 설계·구현.
- SBGrid 기반 데이터 입력·조회·Excel 흐름의 공통화.
- 기술 스택 선정과 초기 기술 검토 주도, 개발 가이드라인 수립·전파, 팀원 코드 리뷰와 품질 관리.

SBUx와 SBGrid는 외부 제품입니다. 저는 제품을 둘러싼 공통 구조와 통합 코드를 설계·구현했습니다. SBGrid API에 직접 작성한 JavaScript를 결합해 여러 업무 화면에서 재사용하는 공통 확장 계층을 구성했습니다.

## 구조를 설계하며 생각했던 것

> 구조는 곧 품질이며, 반복을 줄이는 것이 유지보수의 시작입니다.

화면 상태와 핸들러, 요청, 컴포넌트 초기화, 그리드 편집, 서버 저장까지 전체 사이클을 이해하고 통제하는 구조를 만들고 싶었습니다. 짧은 일정의 0 → 1 프로젝트에서 직접 판단하고 구현하며 아키텍처와 공통 기반을 마련했습니다.

“리액트엔 이런 게 있어요.” 팀원의 한마디는 상태와 요청 규약을 만드는 데 영향을 주었습니다. React 경험이 있던 팀원은 “import랑 vue 전용 태그만 붙이면 그냥 Vue.js네요”라고 말했습니다. 팀이 알아보고 함께 사용할 수 있는 규약을 만들고 싶었습니다.

ViewX는 Vuex 발음에서 착안한 이름이며 **View + State + Context**라는 의미를 담았습니다. exios는 axios의 이름과 API 스타일을 참고했습니다. 두 이름에는 현대적인 프런트엔드 개발에 익숙한 팀원들이 직관적으로 사용할 공통 도구를 만들겠다는 의도가 담겨 있습니다.

저는 이를 **프레임워크의 철학을 구현한 것**이라고 표현했습니다. JavaScript와 공통 UI 연동으로 재사용 가능한 UX 규약을 만드는 접근이었습니다. 이 구조가 개발·유지보수를 단순하게 하고 팀 생산성을 높였다고 느꼈습니다.

[설계 기록](docs/engineering-decisions.ko.md)에는 기존 README의 경험과 같은 주제에 관한 후속 회고를 함께 담았습니다. 검증 책임, Service/ServiceImpl, 비동기 요청 타이밍, 화면·그리드 공통 구조에 관한 판단을 읽을 수 있습니다.

현실적인 제약 안에서 원하는 구조를 실현할 수 있는가에 대한 제 나름의 해답이 담긴 프로젝트입니다. 구조를 깊이 고민하면서 일정과 요구사항에 유연하게 대응하는 실전형 개발자, **사고하는 손**을 가진 개발자이고자 했습니다.

## 프로젝트에서의 설계 논쟁과 경험

### 공통 기반을 우선한 판단: 대표의 요구와 팀원의 피드백

**대표는 제가 직접 업무 화면을 구현하며 진도를 내길 원했습니다.** 눈에 보이는 화면의 완성이 진도를 판단하는 기준이었고, 직접 화면 하나를 구현해 보라는 요구도 받았습니다.

**저는 팀 전체가 사용할 공통 기반과 개발 규약을 우선했습니다.** 그 화면을 포함한 여러 업무 화면을 팀원들이 일관된 방식으로 구현할 수 있도록, 화면 상태·요청·그리드 동작을 연결하는 구조에 집중했습니다. 개별 화면의 완성과 팀 전체의 개발 기반이라는 진도 판단의 차이였습니다.

그리드 기본 동작을 구현하는 단계부터 숫자 정렬과 빈값 검증에 관한 수정 요구도 들어왔습니다. 공통 동작을 먼저 완성하고 세부 검증과 표시 규칙을 후속 단계에서 다듬는 순서를 선택했습니다.

**공통 구조를 사용한 팀원들은 화면 개발이 쉬워졌다는 긍정적인 피드백을 주었습니다.** 당시 들었던 말이 기억에 남습니다.

> “기간도 짧은데 이 정도로 컨트롤하면서 진도 빼는 사람 처음 봤다.”
>
> “페이지 만드는 게 진짜 쉬워졌다. 특히 JSP를 처음 하는데도 무리 없다.”

### 오류 메시지 정책: 기술이사와의 의견 차이

한 기술이사는 DB 오류가 발생했을 때 어느 필드에서 오류가 났는지 서버가 상세히 응답해야 한다고 주장했습니다. 저는 유효하지 않은 입력을 프런트엔드에서 즉시 감지하고, 사용자가 작업하는 자리에서 피드백을 주는 방식이 더 낫다고 판단했습니다.

최종적으로 프런트엔드가 실시간 검증과 상세한 사용자 안내를 맡고, 서버는 요청의 유효성을 판단하면서 보안을 위해 최소한의 정보를 제공하는 정책을 선택했습니다. 저는 이 역할 구분이 전체 사이클과 유지보수를 단순하게 했다고 느꼈고, 프런트엔드 개발자들로부터도 “예상 외로 쉽고, 명확했다”는 피드백을 받았습니다.

### Service/ServiceImpl: 팀 내 구조 선택 논쟁

일부 개발자는 서비스 인터페이스를 분리하면 Mock 구현체와 향후 대체 구현을 추가하기 수월하다며 확장성과 유연성을 강조했습니다. 저는 SI 프로젝트에서 대체 구현이 생기는 빈도와 계층 추가에 따른 복잡도·실수 가능성, 구현·유지보수 비용을 함께 고려했습니다.

팀은 단일 구체 서비스 클래스 구조를 선택했습니다. 저는 이 선택이 개발 속도와 가독성을 높이고 유지보수를 단순하게 했다고 느꼈습니다. 짧은 일정 안에서 팀이 구현하고 유지할 수 있는 구조를 우선한 판단이었습니다.

### exios: 화면 전환과 비동기 응답의 타이밍

SPA 방식 화면 전환 중 이전 화면의 오래 걸리는 조회가 이동 뒤에 응답하면서 다음 화면에 렌더링되는 경험이 있었습니다. 당시에는 페이지 전환과 분리된 JavaScript 모듈 사이의 타이밍이 맞물렸다고 회고했습니다.

제가 기억하는 개선 방향은 응답 도착 시 유효성 조건을 다시 확인하고, 일정 시점 이후의 요청을 무시하거나 폐기하는 구조였습니다. 이 경험을 통해 비동기 환경에서 상태 보존과 무효화, 요청 타이밍 통제의 중요성을 체감했습니다.
